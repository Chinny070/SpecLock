## Native escrow and appeal bonds: failed, root-caused, fixed; live re-verification pending a platform outage

Capabilities #3 and #29 deserve a direct note since their status reflects genuine engineering work across two passes, not a gap left untried. **First pass**: a real payable `fund_agreement`/`settle` design using `gl.get_contract_at(...).emit_transfer(...)` was built, deployed, and live-tested. Incoming deposits worked; the outgoing payout to a plain wallet (EOA) failed with `"Contract ... not found"`. **Second pass**: the root cause was identified — `get_contract_at` addresses another GenLayer intelligent contract, not a general-purpose value-transfer primitive, so that error was the correct behavior for the wrong tool, not a runtime bug. The fix, `gl.evm.contract_interface` (an EVM-layer proxy, `_EthAccount`), was found by inspecting a sibling project in this account (AgentCourt) that solved the identical problem on the identical pinned runner and network, with real live proof it works (a disposable wallet's balance genuinely moved via this exact call). SpecLock's contract now uses this fix: payable `fund_agreement`/`file_appeal`, a pull-payment `claimable` balance credited by `_settle`/`resolve_appeal`, and a new `withdraw()` method. 52/52 Direct Mode tests pass. Two attempts to redeploy and live-verify this fix were both blocked by a Studio Network outage where freshly deployed contracts were unreachable for any subsequent call despite their deploy transactions genuinely finalizing with real consensus — confirmed via raw RPC calls bypassing the CLI/SDK, and confirmed not a general outage since the same calls against a pre-existing deployment succeeded normally. Per instruction, this was not retried further. Full evidence: `docs/DEPLOYMENT.md` "Native-value escrow", `DECISION.md` items 8 and 10.

## What changed since the previous matrix (this audit pass)

- **Two complete real on-chain lifecycles executed and verified**, end to end, via GenLayer's own documented `genlayer-js` SDK (not the CLI, which has its own separate argument-encoding defect — see `docs/DEPLOYMENT.md`): agreement `"2"` (negative case, `httpbin.org/status/200`) ran `create_agreement → accept_agreement → fund_agreement → freeze_agreement → submit_evidence → request_evaluation → finalize_verdict ×2 → settle`, landing on a real on-chain `overall_finding:"FAIL"` and `terminal_phase:"SETTLED"` with `refunded_to_buyer:1000`. Agreement `"4"` (positive case, `httpbin.org/json`) ran the identical sequence to a real `overall_finding:"PASS"`, `SETTLED`, `released_to_provider:1000`. Neither outcome was assumed — both were read back from the chain after the evaluation executed. This promotes capabilities #1, #2, #7, #8, #12, #15, #18, #20, #22, #31, #34 to `IMPLEMENTED_VERIFIED`.

Fixed and redeployed; see `DECISION.md` item 7 and `docs/DEPLOYMENT.md`.
- **#5 Intelligent semantic delivery evaluation**: now PARTIAL with a precise split — the API sub-profile is `IMPLEMENTED_VERIFIED` (both real evaluations above exercised it under genuine consensus); the agent sub-profile remains `IMPLEMENTED_LOCAL_ONLY` (the evidence-fetch fix is deployed but no `ai_agent_delivery` agreement has been created against the live contract yet).

- **#12 Deadline enforcement**: PARTIAL → IMPLEMENTED_VERIFIED. The caller-supplied-timestamp design was audited, found manipulable, and replaced with mutual-consent gates; both real `finalize_verdict` sequences above exercised the two-call consent mechanism exactly as designed.
