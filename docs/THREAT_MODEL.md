# Threat model

## Why not a plain deterministic contract, and why not a centralized LLM/operator

A deterministic contract cannot decide whether a delivered API or AI-agent task output *semantically* satisfies a natural-language acceptance criterion — that requires reading evidence and applying judgment, which is exactly the class of decision GenLayer's validator-consensus model exists to make safely reproducible. A single centralized LLM or human operator is not acceptable either: it is a single point of failure/collusion with no independent check, and SpecLock's entire purpose is to make that judgment independently reproduced and compared by validators (`gl.vm.run_nondet_unsafe` with a custom validator function — see `docs/CONSENSUS.md`), not asserted once and trusted.

## Evidence trust

- **Who controls each source:** API evidence URLs point at the provider-controlled service being evaluated; agent evidence URLs point at provider-controlled or buyer-controlled artifact hosts. Neither party is trusted — every criterion's judgment function independently re-fetches/re-derives rather than trusting the leader's claimed observation (see `docs/CONSENSUS.md`).
- **Stability / snapshot:** `submit_evidence` records a submitter-declared `content_digest` and a URL; `request_evaluation` freezes all submitted-but-not-yet-frozen evidence and computes `_evidence_snapshot_commitment` (a hash over frozen receipt ids + digests) before invoking evaluation, so the evidence set judged is fixed and auditable even though the remote content itself can still change or vanish afterward (a live URL is not content-addressed storage).
- **When a claim must stay UNVERIFIABLE:** any criterion with no matching evidence, or whose independent re-observation fails to reach validator agreement, derives `UNVERIFIABLE`/`INSUFFICIENT` rather than silently defaulting to PASS or FAIL (`_probe_api_criterion`, `_judge_agent_criterion`).

## Threats and how SpecLock addresses or defers them

| Threat | Handling |
|---|---|
| Malicious buyer/provider (false accusation, refusal to acknowledge, fake success) | Only parties to the specific agreement can call its write methods (`_is_party`); overall verdict is derived from independently-judged per-criterion findings, not either party's say-so. |
| Fabricated endpoints / misleading HTTP 200 | `_probe_api_criterion` distinguishes `reachable` from `functional` and never treats a bare 200 as delivery; functional check requires a parseable JSON body. |
| Endpoint drift / mutable response / stale snapshot | Each validator re-fetches at evaluation time; `evidence_snapshot_commitment` records what evidence set was judged, but the module docstring and `docs/GENLAYER_CAPABILITIES.md` are explicit that a live HTTP resource cannot be guaranteed replayable later (capability 38 honesty requirement). |
| URL/SSRF tricks (localhost, private ranges, embedded credentials, non-HTTPS) | The current deployed source rejects non-HTTPS, embedded userinfo, canonical and legacy numeric nonpublic IP literals, scoped literals, and local hostname suffixes. This is defense-in-depth; DNS rebinding and the actual GenVM egress policy are not proven, and the added hostile URL cases have not been exercised in a live evaluation on this release. |
| Prompt injection inside web pages / agent traces | The agent-profile judge prompt explicitly instructs the model to treat quoted evidence as untrusted data, never instructions (`_judge_agent_criterion`). This is a mitigation, not a proof — LLM prompt-injection resistance cannot be verified deterministically, which is exactly why the validator reruns the judgment independently rather than trusting a single leader pass. |
| Forged attestations / self-reported tool logs | The agent profile's docstring and tests (`test_speclock_agent.py::test_agent_missing_artifact_without_independent_evidence_is_unverifiable`) make unresolved/self-only evidence `UNVERIFIABLE`, not `PASS`. |
| Adversarial leader output / forged "PASS" | `validator_fn` in both `_probe_api_criterion` and `_judge_agent_criterion` independently re-derives decision-critical fields. Live consensus evaluations are recorded for the deployed release, but a client cannot force validator misconduct or directly demonstrate a malicious-leader rejection branch. |
| Validators seeing different evidence / consensus non-finality / equivocation | Evidence is frozen before evaluation and its commitment is recorded. Prior release evaluations completed under live Studionet consensus; lifecycle behavior on the current deployment is not yet verified. |
| Replay / double settlement | `settle()` requires `agreement.settlement_id == ""`; `recover_inconclusive()` requires phase `RECOVERY_PENDING` (a settle() side effect), so neither can fire twice on the same agreement. Covered by `test_settlement_conservation_on_pass`'s explicit double-settle-rejected assertion. |
| Unauthorized refunds / arbitrary payout amounts | All settlement amounts are computed deterministically from the finalized evaluation's `overall_finding`/`findings`, never from the nondeterministic judgment text itself (Section 5 "core pattern": nondet answers *what the evidence shows*, deterministic code answers *what that authorizes*). |
| Appeal spam / replay | `max_appeal_rounds` bounds appeal rounds per agreement (default `MAX_APPEAL_ROUNDS = 2`); a resolved appeal's `resolution` moves out of `FILED_UNADJUDICATED` so it cannot be re-resolved; `test_appeal_replay_after_resolution_rejected` exercises the round cap. |
| DoS via huge inputs / unbounded histories / duplicate IDs | `MAX_CRITERIA`, `MAX_SPEC_CHARS`, `MAX_CRITERION_CHARS`, `MAX_EVIDENCE_URL_CHARS`, `MAX_EVIDENCE_METADATA_CHARS`, `MAX_EVIDENCE_PER_AGREEMENT`, `MAX_APPEAL_GROUNDS_CHARS`, `MAX_FETCH_BYTES`, `PAGE_SIZE_MAX`, and duplicate-criterion-id rejection in `_compile_criteria` are all enforced and tested (`test_speclock_security.py`). |
| Sybil reputation / duplicate-count gaming | Reputation only updates in `finalize_verdict` (post-appeal-window, once per agreement's single finalize call), never on a provisional verdict; `test_reputation_only_updates_on_finalized_outcome` asserts this. |
| Privacy leaks | No credentials or off-chain secrets are accepted or stored; evidence URLs are rejected if they embed userinfo. Full evidence content is not stored on-chain (only digest+URL+metadata), per the brief's privacy requirement — but see the caveat below. |
| Self-interested party abusing an unverifiable claimed timestamp to force premature finality or indefinite contestability | **Fixed by redesign, not merely accepted.** An earlier revision let any party supply a caller-asserted `now` for deadline/appeal-window checks; audited and rejected because a party could always choose a `now` that served them. Deadlines are now enforced with no claimed time at all: `finalize_verdict` requires both buyer and provider to separately consent before a provisional verdict finalizes, and `cancel_or_expire` from FROZEN requires both parties' consent before funds are refunded — a lone party cannot force either transition (see `tests/direct/test_speclock_security.py::test_finalize_consent_cannot_be_forced_by_a_single_malicious_party` and `tests/direct/test_speclock_lifecycle.py::test_frozen_wind_down_requires_both_parties_consent`). `file_appeal` has no window to manipulate at all — it is available any time a provisional verdict stands, bounded only by the deterministic `max_appeal_rounds` counter. See `DECISION.md` item 1 and `docs/GENLAYER_CAPABILITIES.md`. |

## Deadline source and post-deadline evidence (2026-10-18)

The prior caller-supplied `now` design was unsafe: a party could claim a timestamp on either side of a deadline to force or delay a transition. The contract reads GenVM transaction-pinned time through `datetime.now(timezone.utc)`, as described by GenLayer's [official Transaction Context documentation](https://docs.genlayer.com/developers/intelligent-contracts/features/transaction-context). Callers cannot pass or change this value; validators observe a consistent transaction timestamp.

The latest local candidate closes a separate unfair-refund path:

- Evidence submission is accepted through the exact deadline (`now <= deadline`) and rejected afterward. After delivery expiry, no evidence means permissionless expiry refunds the agreement.
- If a receipt was submitted on time but has not been evaluated, direct overdue evaluation or `cancel_or_expire` routes it to the existing validator-backed evaluator. No payment is selected until that finding proceeds through the ordinary appeal, finality, and settlement guards.
- If an evaluation already exists and a resubmission was requested but no replacement evidence arrived, the old verdict returns to its regular finality path instead of becoming an automatic refund. New replacement evidence is checked against the resubmission deadline from the request time, not the original delivery deadline.
- Milestone expiry checks receipts tagged to that milestone's criterion IDs. It evaluates relevant timely evidence or refunds only that milestone's allocation when no relevant receipt exists.
- Bilateral voluntary early cancellation and the deterministic settlement-conservation equations remain unchanged.

These candidate paths pass Direct Mode regression tests, including exact boundaries, insufficient evidence, permissionless evaluation, no-evidence refunds, resubmission timing, milestone isolation, and fund conservation. The candidate has not yet been deployed, so these corrections are not claimed as Studionet-verified. The previous deployment's mutual early wind-down transaction is historical evidence only; it does not test natural post-deadline behavior.

## Native-value payout failure (found live, root-caused, fixed)

A first real escrow design (payable `fund_agreement`, payouts via `gl.get_contract_at(recipient).emit_transfer(...)` in `_settle`/`resolve_appeal`) was built and deployed for live testing. It genuinely accepted real deposits — a disposable test wallet's balance dropped by exactly the sent amount — but the matching payout to a plain wallet (EOA) recipient failed on-chain: the child transaction reached `FINALIZED` with `result_name:"NO_MAJORITY"`, `value_credited:false`, and a leader-receipt result of `"Contract ... not found"`. Had this shipped, a contract could accept real deposits while permanently failing to pay them back out, with `settle()` already having recorded `SETTLED`/a specific allocation that the actual on-chain balance would never match — a genuine fund-lock and state/reality divergence risk. It was reverted to bookkeeping-only before an earlier deployment specifically to avoid this.

**Root cause found and fixed, not merely avoided.** `gl.get_contract_at(address)` addresses another GenLayer *intelligent contract* — pointing it at a plain wallet and getting `"Contract ... not found"` is the correct, expected behavior of the wrong primitive, not an unexplained runtime quirk. The correct mechanism for paying a plain wallet is `gl.evm.contract_interface`, an EVM-layer proxy (`_EthAccount` in `contracts/speclock.py`) whose `.emit_transfer(value=...)` emits a native `EthSend` rather than attempting to message a GenVM contract. This was confirmed by a sibling project in this account, AgentCourt, which independently solved the identical problem on the identical pinned runner and Studio Network, with real live proof: a disposable wallet's balance genuinely moved via this exact call pattern (`agentcourt/docs/RELEASE_CANDIDATE_VERIFICATION.md` Phase 9). SpecLock's `fund_agreement`/`file_appeal` are payable again; `_settle`/`resolve_appeal` credit a pull-payment `claimable` balance; a new `withdraw()` pays the credited party out via `_EthAccount`. This is Direct-Mode-verified (52/52 tests pass). Two attempts to redeploy and live-verify this specific fix for SpecLock both failed at the constructor-call level: both reached `FINALIZED` consensus but with `execution_result: "ERROR"` and decoded stderr `TypeError: SpecLock.__init__() takes 1 positional argument but 2 were given`, traced (by comparing raw deploy calldata byte-for-byte against the working deployment) to a malformed `genlayer deploy --args '[]'` CLI invocation — the variadic `--args` flag passed the literal string `"[]"` as one extra constructor argument rather than parsing it as an empty array. Not a platform or contract issue — corrected by omitting `--args` entirely, redeployed to `0xbE2a98135e41B4fE722919b87024D867F8De8343`, and **fully live-verified**: real `PASS` and `FAIL`-then-appealed settlements, real deposits, a real appeal bond, and real GEN withdrawals, with every independent wallet balance delta matching the contract's accounting exactly. See `docs/DEPLOYMENT.md` "Native-value escrow: live-verified" and `DECISION.md` items 8 and 10 for the full evidence on the original failure, this fix, the deploy-command correction, and the live verification.

**Residual risk accepted with this fix**: `withdraw()`'s checks-effects-interactions pattern (zero `claimable` before the external transfer) prevents double-withdrawal and reentrancy — both confirmed live, not just reasoned about (a provider's real second `withdraw()` call correctly reverted, as did a zero-balance party's call) — but means a `claimable` credit that is zeroed and then fails to actually transfer (for any reason) cannot be reconciled from on-chain state alone — a liveness risk, not an integrity one, and the same tradeoff AgentCourt's identical pattern accepts. See `docs/SECURITY.md` for the full audit.

## Confidentiality caveat

A content digest alone proves commitment, not that validators could independently inspect the underlying content, and SpecLock does not claim otherwise: evidence URLs must be publicly fetchable `https` resources for the evaluators to functionally re-derive anything (unreachable/private evidence resolves to `UNVERIFIABLE`/`INSUFFICIENT`, never silently trusted).
