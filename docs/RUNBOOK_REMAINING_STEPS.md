## 1. `recover_inconclusive` — DONE, live on the final deployment

Agreement `"6"` (on the predecessor deployment) remains stuck in `RECOVERY_PENDING` — its disposable buyer/provider keys existed only inside the Node process that generated them and cannot be reused from a fresh invocation, the same issue that stranded an earlier agreement `"3"` on a different, older deployment. Rather than treat that as a dead end, a fresh one-shot agreement was created on the **final** deployment specifically to reach `recover_inconclusive` in the same process: the same evidence/criterion mismatch again produced a genuine `UNVERIFIABLE`, `settle()` moved it to `RECOVERY_PENDING`, and `recover_inconclusive` was called and completed the refund — confirmed by reading back `get_agreement`/`get_settlement` afterward (`phase:"REFUNDED"`, `refunded_to_buyer:1000`). Full transaction evidence in `docs/DEPLOYMENT.md` "`recover_inconclusive` — live, verified, on the final deployment". Already covered functionally by `tests/direct/test_speclock_security.py::test_unverifiable_overall_recovers_funds_without_awarding_either_party` as well.

## 2. Native escrow verification (capability #3) — attempted, found unsafe, reverted

A real `@gl.public.write.payable` `fund_agreement` plus `emit_transfer`-based payouts in `_settle`/`resolve_appeal` were implemented, deployed (`0xaa54c150B128843e5638cF31e2F1B632117ccBE2`), and tested against a funded signer. Deposits genuinely worked; payouts to a plain wallet (EOA) recipient failed on-chain (`result_name:"NO_MAJORITY"`, `value_credited:false`, decoded `"Contract ... not found"`). The design was reverted back to bookkeeping-only to avoid shipping a fund-lock hazard. This is a confirmed runtime limitation with full transaction evidence, not an unattempted scope item — see `docs/DEPLOYMENT.md` "Native-value escrow: attempted, found unsafe, reverted", `docs/THREAT_MODEL.md`, `docs/SECURITY.md`, `DECISION.md` item 8.

## How to reproduce or extend the lifecycle tests already run

See `docs/DEPLOYMENT.md` "How real on-chain lifecycle execution was achieved" for the full method: `npm install genlayer-js` in a scratch directory, generate a fresh disposable buyer/provider pair with `createAccount()` per agreement, fund both from a wallet you control via `genlayer account send`, then run the full `create_agreement → accept_agreement → fund_agreement → freeze_agreement → submit_evidence → request_evaluation → finalize_verdict ×2 → settle` sequence in one script process (`createAccount()` never exposes a raw private key, so a generated account cannot be reused across separate process invocations — this is what stranded agreement `"3"` on an earlier deployment).
