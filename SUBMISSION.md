## What SpecLock is

A single canonical GenLayer Intelligent Contract (`contracts/speclock.py`) for universal digital-delivery agreement and adjudication, with two fully-implemented evaluation profiles (API delivery, AI-agent delivery) sharing one typed lifecycle/evidence/evaluation/appeal/settlement state machine.

## What consensus actually protects here — now proven live, not just by design

For every criterion judgment, the leader's observation is independently re-derived by every validator (`gl.vm.run_nondet_unsafe` with a custom validator function — see `docs/CONSENSUS.md`) and only the decision-critical fields are compared, never the leader's narrative alone. Across the project's deployment history, **four complete agreement lifecycles were executed and settled on GenLayer Studio Network, across both evaluation profiles**, each `create_agreement → accept_agreement → fund_agreement → freeze_agreement → submit_evidence → request_evaluation → finalize_verdict ×2 → settle`, every step `FINALIZED` under real multi-validator consensus. Current candidate-specific lifecycle evidence is listed separately above.

API-delivery: real validators independently fetched `https://httpbin.org/status/200` and correctly derived `overall_finding:"FAIL"` (reachable, HTTP 200, non-JSON body); real validators independently fetched `https://httpbin.org/json` and correctly derived `overall_finding:"PASS"`. Both settled exactly matching the deterministic rules (`FAIL` → full refund to buyer; `PASS` → full release to provider).

AI-agent-delivery: real validators independently fetched `https://httpbin.org/robots.txt` and the LLM's rationale genuinely quoted the fetched content, deriving `overall_finding:"PASS"` for a matching criterion. For a second criterion that described an artifact never actually delivered, the model did **not** guess `FAIL` — it correctly returned `UNVERIFIABLE`, unscripted real reasoning, which in turn correctly triggered `settle()`'s fund-recovery branch (`terminal_phase:"RECOVERY_PENDING"`, full amount retained, neither party credited) rather than awarding anyone on an inconclusive verdict.

No outcome across any of the four was assumed in advance — all were read back from the chain after each evaluation actually executed. Full transaction-by-transaction evidence in `docs/DEPLOYMENT.md`.

## What a dedicated security audit of this contract found and fixed

A follow-up review specifically asked whether an untrusted caller could manipulate deadlines, appeal windows, or settlement timing. The original design (a caller-supplied `now` timestamp checked against a monotonic ratchet) **could not be proven safe** — a self-interested party could always choose a value that served them, in either direction. It has been replaced: no part of this contract depends on any party's claim about elapsed time. `finalize_verdict` (from a provisional verdict with no appeal) and the FROZEN branch of `cancel_or_expire` now require both buyer and provider to separately consent before taking effect, which a lone party cannot force. `file_appeal` was never time-boxed to begin with. This mutual-consent mechanism was exercised live on both real settled agreements above (each `finalize_verdict` was called once per party; the first call returned `false`, the second `true`). See `DECISION.md` item 1, `docs/THREAT_MODEL.md` "clock redesign", and `tests/direct/test_speclock_security.py::test_finalize_consent_cannot_be_forced_by_a_single_malicious_party`.

The same review pass also found and fixed a real defect in `resolve_appeal` (an appeal would always resolve `UPHELD` on the first round regardless of outcome — see `docs/CONSENSUS.md` "Appeal resolution precision") and, during live Studionet testing, a real defect in `_as_address` (`TypeError: string argument without an encoding` when an address argument arrived as a plain hex string, the convention used by `genlayer-js`'s standard API — see `DECISION.md` item 7). Both are fixed and covered by regression tests.

## Native-value escrow: failed, root-caused, fixed, redeployed

A first payable-deposit / `emit_transfer`-payout escrow design was implemented and deployed for live testing (`0xaa54c150B128843e5638cF31e2F1B632117ccBE2`). **Deposits genuinely worked**: a disposable test wallet's real balance dropped by exactly the amount sent. **Payouts did not**: the transfer to a plain wallet (EOA) recipient reached `FINALIZED` with `result_name:"NO_MAJORITY"` and a leader-receipt result that decodes to `"Contract ... not found"`.

**This was then root-caused and fixed, not merely documented as a limitation.** `gl.get_contract_at(address)` addresses another GenLayer *intelligent contract* — it is the wrong primitive for paying a plain wallet, and its failure there is correct, expected behavior. The fix, `gl.evm.contract_interface` (an EVM-layer proxy, `_EthAccount` in `contracts/speclock.py`), was independently live-verified. `fund_agreement`/`file_appeal` are payable; settlement credits pull-payment balances; `withdraw()` pays them through `_EthAccount`. Historical escrow coverage was 52/52 tests; the corrected current source passes 89/89, and its latest-release section records real deposits, settlement and withdrawals.

**Two redeploy attempts to verify this for SpecLock itself initially looked blocked, then turned out to be a CLI invocation mistake, not a platform or contract issue.** Both fresh deployments reached `status_name: "FINALIZED"` with real 5-validator consensus — which a first pass mistook for success — but their leader receipts actually carried `execution_result: "ERROR"`, decoding to `TypeError: SpecLock.__init__() takes 1 positional argument but 2 were given`. Comparing raw deploy calldata byte-for-byte against the working deployment found the cause: the deploy command used `--args '[]'`, and the CLI's variadic `--args` flag passed that single-quoted shell token through as one literal string constructor argument, not an empty array. Corrected by omitting `--args` entirely (matching AgentCourt's own documented working invocation), redeployed to `0xbE2a98135e41B4fE722919b87024D867F8De8343` (`FINALIZED`, `execution_result: "SUCCESS"`, confirmed via a working `genlayer schema` readback).

**Then fully live-verified with real GEN moving in both directions.** Two complete agreements were run under an explicit budget (max 0.001 GEN per transaction, max 0.02 GEN cumulative; actual spend 0.00068 GEN): a real `PASS` settlement where the provider called `withdraw()` and received a real payout — independent `getBalance` check showed the provider's wallet increase by exactly the settled amount — and a real `FAIL` settlement that was appealed with a real bond, correctly `REJECTED` on re-evaluation against unchanged evidence, with the bond correctly credited to the non-appellant party and withdrawn for real. A second `withdraw()` by the same provider correctly reverted (double-withdrawal prevented); a `withdraw()` by a party with zero claimable balance correctly reverted (no-balance withdrawal rejected). **No contract defects were found** — every outcome matched Direct Mode's existing predictions exactly. Full transaction-by-transaction record: `docs/DEPLOYMENT.md` "Native-value escrow: live-verified".

## Capability audit: all 38 numbered brief items, two passes

**First pass** (`docs/FEATURE_MATRIX.md`) traced every one of the 38 numbered capabilities to its implementing method(s), its Direct Mode test(s), and its live-network verification status. Writing a Direct Mode probe for the **full** `request_resubmission` cycle — something no existing test exercised — found that `submit_evidence` never advanced the agreement's phase out of `RESUBMISSION_REQUESTED`, so a new evaluation could never be requested again: a genuine, previously-untested fund-lock, with no escape since `cancel_or_expire`'s wind-down also only accepted `FROZEN`. A related defect meant that even after fixing the phase transition, a resubmission's corrected evidence was silently ignored on re-evaluation (the API evaluator always re-probed the first, stale evidence for a criterion rather than the latest). Both fixed and live-verified end to end: a real agreement evaluated `FAIL`, was resubmitted, corrected evidence was submitted, and re-evaluation produced a genuine `PASS`. This pass also credited several capabilities with live evidence already gathered in earlier runs that the matrix had never reflected (appeal, evidence freeze, finding-specific challenges, web-evidence fetching, evidence-quality bands).

**Second pass** targeted the 8 capabilities the first pass left `PARTIAL`/`NOT_IMPLEMENTED`/`LOCAL_ONLY` (#13, #19, #21, #25, #26, #30, #33, #38):
- **#13 (partial payments) — fixed and live-verified.** `_derive_overall` now deterministically escalates to `PARTIAL` once every required criterion is satisfied but an optional one is not, no longer dependent on a nondeterministic LLM output. A real two-criterion agreement derived `PARTIAL` live and settled with a real `50000000000000`/`50000000000000` proportional split.
- **#19 (independence/corroboration) — fixed, Direct-Mode-proven both ways, and now live-verified.** Current agreement `5` used pinned README bytes: different parties/hosts produced `PASS/SUFFICIENT`; same-party records across two hosts produced `PASS/INSUFFICIENT` with the deterministic auto-downgrade rationale. Since both URLs mirrored the same underlying document, this verifies the party/host heuristic but not genuine source independence.
- **#21 (adversarial checks) — a real SSRF bypass found and fixed, live-verified.** An IPv6-literal evidence URL (`https://[::1]/...`) bypassed the host blocklist because the port-stripping logic also split the IPv6 address itself apart. Fixed, and the fix demonstrated live: a real `https://[::1]/health` submission was correctly rejected on-chain.
- **#25 (procedural review) — a new, bounded, mutual-consent-gated tier added and live-verified.** Available only once ordinary appeal rounds are exhausted, usable exactly once. Live: two real appeal rounds were exhausted, a third correctly reverted, one party's request returned `false`, the other's triggered a genuine full re-evaluation, and a further request correctly reverted.
- **#26 (narrower appeal re-evaluation) — fixed and live-verified.** `resolve_appeal` now re-judges only the specifically-challenged criteria; unchallenged criteria are carried forward verbatim. Live: a real two-criterion agreement was appealed twice (challenging only one criterion both times), and the other criterion's finding was read back unchanged across both rounds.
- **#38 (deterministic replay/audit) — the strongest honestly supportable form added and live-verified.** A new on-chain view, `verify_settlement_replay`, recomputes a settlement from its recorded evaluation using the exact function `settle()` itself calls, and reports whether they match. Explicitly NOT exact execution replay (the original live observation is never re-run). Live: returned `matches_recorded_settlement:true` against a real settled agreement.
- **#12 (deadline enforcement) — reclassified, not newly broken.** Mutual consent closes the *manipulation* hole completely but provides no *liveness* guarantee: if either party goes silent after appeals are exhausted, the agreement can remain stuck permanently, with no unilateral escape (the new #25 tier is also mutual-consent-gated, for the identical reason). Downgraded from `IMPLEMENTED_VERIFIED` to `PARTIAL` to reflect this honestly rather than leave an over-claimed status standing — see `docs/THREAT_MODEL.md`.
- **#35 — documented as the same mechanism as #14, not a distinct feature**, so the capability count is not misread as more distinct functionality than actually exists.
- **#30 and #33 were implemented in a later pass** (commit `85d4f96`): milestones and warranty holdbacks have Direct Mode coverage and real Studionet lifecycle evidence. The latest `0xe52F…` release additionally verifies rejected-payable refunds and strict warranty digest binding. #33 remains `PARTIAL` only because the runtime has no trustworthy clock for a finite claim window; see the current matrix and deployment ledger.
