## Product decision (fixed by the brief, recorded here for traceability)

SpecLock is one canonical GenLayer Intelligent Contract (`contracts/speclock.py`) implementing a universal digital-delivery agreement/adjudication primitive, with two fully-implemented evaluation profiles: **API delivery** and **AI-agent delivery**. No marketplace frontend, database, or off-chain adjudicator was added — only the contract, Direct Mode tests, fixtures, and docs.

## Material findings that shaped the design (discovered empirically, not assumed)

1. **No block timestamp is exposed to contract code — and the redesign history matters.** `gl.message` (via `genlayer.gl.MessageType`) exposes only `contract_address`, `sender_address`, `origin_address`, `value`, `chain_id`. A first revision of this contract accepted a caller-supplied `now: int` (unix seconds) on every time-gated write call, advanced through a monotonic ratchet (`_advance_clock`). **A follow-up audit (prompted by an explicit review request) rejected that design**: a self-interested party could always pick a `now` that served them — an early value to keep contesting an unfavorable verdict, or a late value to force the counterparty's appeal window closed — and the contract had no way to check either claim against real elapsed time. The SDK does define a `message_raw['datetime']` field (confirmed present in `genlayer/_internal/msg.py` and re-exported via `genlayer/gl/__init__.py`'s `__all__`), which looked like it might be the intended mechanism — but tracing the installed `genlayer-test` 0.29.2 Direct Mode harness found that its own `get_message_raw()` helper (the only place that would refresh `datetime` to reflect `vm.warp()`) is unreferenced dead code in this version, so even that path could not be verified to work correctly here. **Historical design (superseded by item 14 below): no caller-asserted time anywhere.** Every transition that needed "has enough time passed" is replaced by either (a) an actual appeal being filed — never time-boxed, bounded only by `max_appeal_rounds` — or (b) both buyer and provider explicitly and separately consenting (`finalize_verdict` from a provisional verdict with no appeal filed; `cancel_or_expire` from FROZEN). A purely contract-internal monotonic counter (`_next_seq`, zero attacker input) replaces wall-clock stamps for audit ordering only — nothing security-relevant is gated on it. See `docs/GENLAYER_CAPABILITIES.md` and `docs/THREAT_MODEL.md` for the full writeup, and `tests/direct/test_speclock_security.py::test_finalize_consent_cannot_be_forced_by_a_single_malicious_party` for the proof this closes the original vulnerability.
2. **`gl.message.sender_account` does not exist** — the correct field is `sender_address`. This was caught by a failing Direct Mode test, not by inspection alone.
3. **Address-typed public method parameters can arrive as raw `bytes`** after the Direct Mode harness's calldata round-trip in this installed version, rather than a reconstructed `Address`. The contract defensively coerces with `_as_address()` at every public-method Address parameter boundary rather than assuming the SDK always hands back a typed object.
4. **`DynArray`/nested `TreeMap` values cannot be constructed directly** (`DynArray[str]()` raises `TypeError: this class can't be instantiated by user`), and a `TreeMap.__getitem__` on a missing key raises `KeyError` rather than auto-vivifying. The working pattern is `TreeMap.get_or_insert_default(key)`.
5. **`from __future__ import annotations` breaks ABI schema extraction.** With it active, all type hints become strings at runtime, and GenLayer's `get_schema()` (which reads `inspect.signature(...).annotation` directly, not via `typing.get_type_hints`) cannot resolve them — `genvm-lint validate` fails with "couldn't get schema" pointing at the first public method alphabetically, which is misleading about the real cause. The contract does not use that import.

6. **A real logic bug was found and fixed in `resolve_appeal` during the same audit pass**: it compared the new re-evaluation's `overall_finding` against `self.evaluations[appeal.resolution_evaluation_id]` — a field that is never populated before `resolve_appeal` itself sets it, so the lookup always produced `None` and every first-round appeal was unconditionally resolved `UPHELD`, regardless of whether the challenged finding had actually changed. Fixed to compare the specific challenged criteria's findings between the challenged evaluation (captured before re-evaluation) and the new one. See `tests/direct/test_speclock_consensus.py::test_appeal_rejected_when_challenged_finding_does_not_actually_change` and `::test_appeal_upheld_when_challenged_finding_genuinely_changes`.
7. **`_as_address` crashed on a plain hex-string address — found via a real failed on-chain transaction, not in testing.** The genlayer CLI's `addr#...` literal syntax (used for every call so far via that CLI) constructs a typed `Address`/bytes value, which `_as_address`'s `bytes(value)` handled fine. Calling `create_agreement` through `genlayer-js`'s standard, documented `writeContract` API — the same SDK the CLI itself is built on — passes an address argument as a plain `"0x..."` string, and `bytes("0x...")` without an explicit encoding raises `TypeError: string argument without an encoding` in Python. This executed as a real `ERROR`-status transaction on Studio Network before the fix (visible in that transaction's `leader_receipt.genvm_result.stderr`). Fixed by decoding a `str` input as hex before constructing the `Address`. This means any standard GenLayer client passing addresses as plain hex strings — plausibly including the Studio web UI — would have hit this on any prior deployment. See `tests/direct/test_speclock_lifecycle.py::test_provider_as_plain_hex_string_address_is_accepted` and `docs/DEPLOYMENT.md`.
8. **Real native-value escrow and appeal bonds were built, deployed, live-tested, and then deliberately reverted** after live testing showed a serious fund-lock hazard, not a contract bug. `gl.get_contract_at(address).emit_transfer(value=..., on=...)` is GenVM's documented mechanism for a contract to pay out native value, and `@gl.public.write.payable` + `gl.message.value` is the documented way to receive it. The **incoming** leg genuinely works: a real disposable buyer wallet's balance dropped by exactly the sent amount (1 GEN) when calling a payable `fund_agreement`, and the contract correctly recorded that real value. The **outgoing** leg does not: `settle()`'s `emit_transfer` to the provider (a plain wallet address, exactly what a real buyer/provider normally is) produced a child transaction that reached `FINALIZED` with `result_name: "NO_MAJORITY"` and `value_credited: false`, and its leader receipt's raw result decodes to the literal string `"Contract 0x...not found"` — this GenVM runtime's `emit_transfer` appears to require the recipient to be a deployed contract, not an ordinary wallet address. The disposition of the escrowed 1 GEN after that failed transfer was not conclusively established (checked: not in the contract's balance, not credited to the provider, buyer's balance had already debited it) — that uncertainty is itself part of the finding, not swept aside. Because shipping this would let real deposits succeed while payouts silently and permanently fail, the entire real-escrow and bond design was reverted back to bookkeeping-only before the final deployment, and the dead-end is documented in `fund_agreement`'s docstring and `docs/DEPLOYMENT.md` rather than hidden. No smaller fix was available within this pass's time budget — the correct fix would need either a different GenVM primitive for paying plain wallets (none was found in the installed SDK) or confirmation from GenLayer that `emit_transfer` to an EOA is expected to work on a different runtime/network configuration.

9. **`recover_inconclusive` was successfully exercised live after being stranded on an earlier deployment by a key-lifetime limitation, not a contract bug.** Agreement `"6"`'s disposable buyer/provider keys exist only inside the `genlayer-js` Node process that generated them (`createAccount()` never exposes a raw private key), so a fresh process cannot sign a follow-up call against that same agreement — the identical issue that had earlier stranded another agreement `"3"` on a different deployment. Rather than leave the capability itself unverified live, a new one-shot agreement was created on the final deployment specifically to reach `recover_inconclusive` within the same process that created it: it reproduced the same evidence/criterion mismatch to get a genuine `UNVERIFIABLE`, `settle()` moved it to `RECOVERY_PENDING`, and `recover_inconclusive` was called successfully — confirmed independently by reading `get_agreement`/`get_settlement` back afterward (`phase:"REFUNDED"`, `refunded_to_buyer:1000`). One operational wrinkle: the script's receipt-polling hit the same transient Studio Network RPC flakiness described elsewhere in this project (an HTML error page instead of JSON) right as the successful call was mining, so the retry wrapper resubmitted the call four more times; each of those four correctly reverted on-chain with `[EXPECTED] nothing to recover`, which is itself independent proof the first call had already succeeded. See `docs/DEPLOYMENT.md` "`recover_inconclusive` — live, verified, on the final deployment".

10. **The native-escrow payout failure (item 8) was root-caused further and fixed.** A sibling project in this account, AgentCourt (`agentcourt/contracts/agent_court.py`), independently solved the exact same problem on the identical pinned runner (`py-genlayer:1jb45aa8ynh2a9c9xn3b7qqh8sm5q93hwfp7jqmwsfhh8jpz09h6`) and the identical Studio Network: `gl.get_contract_at(address)` addresses another GenLayer *intelligent contract* and correctly fails against a plain wallet (EOA) with `"Contract ... not found"` — that is not a bug, it is the wrong primitive for the job. The correct primitive is `gl.evm.contract_interface`, which builds an EVM-layer proxy (`_EthAccount` in `contracts/speclock.py`, same pattern as AgentCourt's) whose `.emit_transfer(value=...)` emits a native `EthSend` to the chain-layer address instead of attempting to message a GenVM contract. AgentCourt's own release-candidate verification (`agentcourt/docs/RELEASE_CANDIDATE_VERIFICATION.md`, Phase 9) recorded a **real** EOA balance change from this exact call (`rc-provider`'s balance `0.001 GEN -> 0.0015 GEN`, tx `0x3dac6d579a6ddd0f92e2eb0fc649f811b4aadd010ed1a97a612dd413869f328c`). SpecLock's `fund_agreement`/`file_appeal` were made payable again, `_settle`/`resolve_appeal` now credit a pull-payment `claimable` balance instead of pushing a transfer, and a new `withdraw()` method pays the caller out via `_EthAccount` — ported deliberately as a pull pattern (never calling `emit_transfer` from inside `_settle` itself) to keep the real transfer in a single, simple, caller-triggered method. This is fully covered by 8 new Direct Mode tests (bond/value mismatches rejected, claimable correctly credited on PASS/FAIL/UNVERIFIABLE/appeal outcomes, `withdraw` zeroing and reverting on empty balance) — 52/52 tests pass, lint is clean.

    **Correction to an earlier conclusion in this same item**: two redeploy attempts to live-verify this fix (`0xd60dfaC9B3473Fce6bC97CD47F7a5Ac80c97A74e`, `0x192CA2229677E4e1d0d115d4665E2634Bf0A25d1`) were initially misdiagnosed as blocked by a Studio Network "deployment-registration outage," because `genlayer receipt --status FINALIZED` reported `FINALIZED` for both and a naive read of that alone looked like success. Re-examining the full receipt found the real signal that check missed: both deploy transactions' leader receipt carried `execution_result: "ERROR"` (not `SUCCESS`), with a decoded stderr traceback reading `TypeError: SpecLock.__init__() takes 1 positional argument but 2 were given`. **Root cause, confirmed by comparing raw deploy calldata byte-for-byte**: the working `0xD5602E88...` deployment's calldata is a single byte (`[6]`, a "zero constructor arguments" marker), while both failing deployments' calldata is 8 bytes encoding `{"args": "[]"}` — i.e. the two-character literal string `"[]"`, not an empty array. This came from the deploy command itself: `genlayer deploy --contract contracts/speclock.py --args '[]'`. The CLI's `--args <args...>` option is variadic (each shell token becomes one separate constructor argument), so the single-quoted shell token `[]` was passed through as one string argument, not parsed as JSON for an empty array — calling `SpecLock.__init__(self, "[]")`, one argument too many, exactly matching the traceback. AgentCourt's own documented working deploy command omits `--args` entirely (`genlayer deploy --contract release/agent_court.py`), confirming this is the correct invocation for a zero-argument constructor. **This was a shell/CLI invocation mistake in this session, not a platform outage and not a contract defect** — both deploy transactions genuinely reached real 5-validator consensus (correctly agreeing the constructor call errored), which is exactly why `--status FINALIZED` alone was a misleading signal; `execution_result` must always be checked alongside `status_name`, a process lesson now recorded here. Redeployed correctly per `docs/DEPLOYMENT.md`.

A second `withdraw()` by the same provider correctly reverted (`"[EXPECTED] nothing to withdraw"`) — double-withdrawal prevented. A `withdraw()` by the buyer, who had zero claimable balance, also correctly reverted — confirming there is no way to withdraw funds credited to someone else, since `withdraw()` takes no address parameter at all. Agreement "2" funded for real, evaluated to a genuine `FAIL`, was appealed with a real bond (`10000000000000` atto), re-evaluated against the same unchanged evidence (still `FAIL`), correctly resolved `"REJECTED"`, correctly credited the bond to the non-appellant party, and both the refund and the bond were withdrawn for real — wallet balance deltas matched the accounting exactly (buyer net `-10000000000000`, i.e. fund+bond out minus refund back in; provider net `+10000000000000`, the bond). **No contract defects were found during this live run**; every outcome matched Direct Mode's existing predictions exactly, so no contract or test changes were made as a result. Full transaction-by-transaction record: `docs/DEPLOYMENT.md` "Native-value escrow: live-verified".


12. **A full capability-by-capability audit of all 38 numbered brief items found and fixed a real fund-lock defect in `request_resubmission`, and promoted 15 capabilities to `IMPLEMENTED_VERIFIED` using evidence already gathered or newly gathered live.** The audit (`docs/FEATURE_MATRIX.md`) traced each capability to its implementing method(s), its Direct Mode test(s), and whatever live-network evidence existed. Two real defects were found:
    - `submit_evidence` only advanced `agreement.phase` from `PHASE_FROZEN` to `PHASE_SUBMITTED` — never from `PHASE_RESUBMISSION_REQUESTED`. Since `request_evaluation` only accepts `PHASE_SUBMITTED`/`PHASE_RE_EVALUATING`, any agreement that called `request_resubmission()` was **permanently stuck**: no further evidence submission could ever unblock a new evaluation, and (compounding it) `cancel_or_expire`'s wind-down path only accepted `PHASE_FROZEN`, so there was no escape even if nobody ever resubmitted — a genuine, previously-untested fund-lock. Caught by writing a Direct Mode probe exercising the *full* resubmission cycle (create → evaluate FAIL → request_resubmission → submit corrected evidence → re-evaluate), which no existing test did (the only prior test of `request_resubmission` was the budget-exhaustion revert case, never the happy path). Fixed in two places: `submit_evidence` now also advances `PHASE_RESUBMISSION_REQUESTED → PHASE_SUBMITTED`, and `cancel_or_expire` now also accepts `PHASE_RESUBMISSION_REQUESTED` for mutual-consent wind-down. Two new regression tests added (`test_resubmission_full_cycle_reaches_a_new_evaluation`, `test_resubmission_requested_without_a_follow_up_can_still_be_wound_down`).
    - A second, related defect in `_evaluate_api_profile`: when multiple evidence records exist for the same criterion (exactly what happens after a resubmission), it probed `probe_evidence[0]` — the **first**, oldest evidence ever submitted — rather than the most recent. This meant even after the fund-lock above was fixed, a resubmission's whole *point* (submitting corrected evidence) was silently ignored on re-evaluation; the stale first submission would be re-probed forever. Fixed to use `probe_evidence[-1]` (latest evidence for a criterion wins).
    - Redeployed (contract code changed) to `0x2671cd7Fc9f7653f8e8A506E4aC3281A1Db0553c` via the now-confirmed-correct `genlayer deploy --contract contracts/speclock.py` (no `--args`), `FINALIZED` with `execution_result: "SUCCESS"`. The full resubmission fix was then live-verified end to end on Studio Network: a real agreement evaluated `FAIL`, `request_resubmission` moved it to `RESUBMISSION_REQUESTED`, corrected evidence was submitted (`SUBMITTED` phase confirmed), re-evaluation produced a genuine `PASS`, and the agreement settled normally with the provider's reputation updating only on the finalized outcome.
    - **Capabilities re-audited and promoted based on evidence**: several capabilities already had genuine live evidence from earlier lifecycle runs that the matrix had never credited (e.g. #9 appeal, #10/#27 evidence freeze, #24 finding-specific challenges — all exercised live in the agreement-B appeal run on the prior deployment; #4 web evidence fetched live on every single evaluation call ever made; #23 evidence-sufficiency bands observed live every time). Others were newly live-verified in this pass with small, budget-compliant transactions on the current deployment: #6 (multi-criterion scoring: a real two-criterion agreement with one `PASS`/one required `FAIL` correctly derived overall `FAIL`), #11 (bounded re-evaluation mechanism exercised via a real appeal), #14/#35 (reputation: read back before/after a real finalize, `0→1` finalized outcome), #16 (spec compiler's acceptance path runs on every live `create_agreement`), #17 (ambiguity detection: a real vague-term spec was flagged, `freeze_agreement` without acknowledgement correctly reverted live, with acknowledgement correctly succeeded), #32 (resubmission, the fix above), #36 (policy fingerprint read back live), #37 (the deterministic/intelligent hybrid architecture, demonstrated by the sum of every other live-verified evaluation). See `docs/FEATURE_MATRIX.md` for the full capability-by-capability table and the precise evidence and remaining gap for every one of the 38.
    - **What remains honestly unresolved**: capability #13 (real PARTIAL settlement split) cannot be forced live — the `PARTIAL` finding is only ever emitted by the agent profile's LLM judge, nondeterministically, never by the deterministic API evaluator; forcing it live isn't reliably possible without gambling transaction budget on an uncontrollable model output, so it remains Direct-Mode-only, honestly. Capabilities #30 (milestones) and #33 (warranty claims) remain `NOT_IMPLEMENTED` — both are genuine, nontrivial scope additions (a milestone ledger of sub-agreements, each with its own criteria/evidence/settlement; a warranty claim window keyed off retained funds) that were not attempted in this pass rather than rushed or faked; now that native-value custody (#3) is live-verified, the remaining blocker for both is purely implementation time, not a technical unknown. Capabilities #19, #21, #25, #26, #38 remain `PARTIAL` for the same precise, previously-documented reasons (deferred independence-assessment rule, no forged-leader-under-consensus test possible, no separate procedural-review tier built, re-evaluation still re-runs every criterion rather than just the challenged ones, and a changed live evidence source is inherently non-replayable).
    - **A small amount of real testnet GEN (0.0001 GEN) is stranded** in agreement `"3"` on the current deployment: its disposable buyer/provider keys exist only in the Node process that created them (the same `createAccount()` limitation documented throughout this project) and a transient Studio Network RPC error during the live session meant the lifecycle was never completed past evaluation. The evaluation evidence itself was fully captured before the process exited. This is the same low-value, already-documented key-lifetime pattern as agreements `"1"` (an earlier stranded DRAFT/ACCEPTED agreement, no funds involved) and the historically-stranded agreements on superseded deployments — not a new class of risk.

13. **A follow-up pass specifically targeted the 8 capabilities the prior audit (item 12) left `PARTIAL`/`NOT_IMPLEMENTED`/`LOCAL_ONLY` (#13, #19, #21, #25, #26, #30, #33, #38), completing five with genuine deterministic mechanisms, fixing one more real security defect, honestly reclassifying one capability that had been over-claimed, and documenting concrete (not vague) blockers for the remaining two.**
    - **#13 (partial payments) — fixed.** `_derive_overall` previously ignored optional criteria entirely once every required criterion passed, so a failed optional criterion had zero effect on the verdict or settlement. It now deterministically escalates to `PARTIAL` when all required criteria are satisfied but an optional one is not — giving `settle()`'s existing proportional-release branch a real, forceable trigger, rather than one only a nondeterministic LLM judge could ever produce.
    - **#19 (multi-source corroboration) — fixed.** `_judge_agent_criterion` now computes `distinct_submitters` deterministically from the frozen evidence records (identically for the leader and every validator, never from the nondet LLM call itself) and downgrades a model's `SUFFICIENT` claim to `INSUFFICIENT` whenever multiple evidence items for one criterion all share a single submitter — enforced regardless of what the model itself concluded, closing the gap where a model could simply assert independence that did not exist.
    - **#21 (adversarial delivery checks) — a real SSRF bypass found and fixed.** Writing a new adversarial boundary test for an IPv6-literal evidence URL (`https://[::1]/...`) found it was NOT rejected by the host blocklist, unlike every IPv4 loopback/private-range variant. Root cause: `_validate_url`'s port-stripping logic (`host.split(":")[0]`) also split the IPv6 address itself apart (it contains colons), leaving `host_only` as just the literal character `"["`, which never matches the `"::1"` blocklist entry. Fixed by stripping the `[...]` bracket notation before matching. This had been present since `_validate_url` was first written and was never previously tested with bracket notation.
    - **#25 (procedural review tier) — added.** A new method, `request_procedural_review`, implements a second, genuinely distinct review tier: available only once ordinary appeal rounds are exhausted, usable exactly once per agreement, and — unlike the unilateral ordinary appeal — requiring BOTH parties' mutual consent (matching the existing `finalize_verdict`/`cancel_or_expire` pattern), since this tier is meant for a genuinely exceptional, irreducible question rather than a routine admissible challenge.
    - **#26 (narrower appeal re-evaluation) — fixed.** `resolve_appeal` previously called the same `request_evaluation` used for the initial evaluation, re-judging every criterion on every appeal round regardless of what was actually challenged. Refactored into a shared `_request_evaluation_impl(restrict_to_ids, carry_forward_findings)` that `resolve_appeal` now calls with only the challenged criterion ids, carrying every unchallenged criterion's prior finding forward verbatim. Proven for real (not just by code reading) with a test that changes an *unchallenged* criterion's live evidence to something that would flip its finding if it were re-judged, and shows it does not flip.
    - **#38 (deterministic replay/audit) — the strongest honestly supportable form added.** A new on-chain view, `verify_settlement_replay(agreement_id)`, recomputes a settlement's amounts from its recorded evaluation via the exact same `_compute_settlement_amounts` function `settle()` itself calls (extracted specifically so the two can never silently drift apart), and reports whether they match what was actually recorded — callable by anyone. This is explicit about the limit it does not cross: it is deterministic-state auditing, not exact historical execution replay (the original live web fetch or LLM judgment is never re-run, and cannot be once a live source changes — see `docs/THREAT_MODEL.md`).
    - **#12 (deadline enforcement) — corrected in the current candidate.** The previous mutual-consent model was not deadline enforcement. The candidate uses the verified transaction-pinned timestamp and routes timely evidence through evaluation after expiry; no-evidence cases refund, evaluated cases follow normal verdict rules, and resubmissions use their own deadline. It is `IMPLEMENTED_LOCAL_ONLY` until clean-clone and live evidence pass; see the matrix and testing report.
    - **#35 (duplicate of #14) — documented, not newly implemented.** The 38-item brief lists "evidence-backed reputation" once under "Foundational" and again under "Transparency"; this project's capability count necessarily numbers it twice, but it is one mechanism, tested and live-verified once. `docs/FEATURE_MATRIX.md` now says this explicitly so a reader does not take "29 of 38 verified" as 29 distinct pieces of functionality when it is 28 distinct mechanisms, one numbered twice.
    - **#30 (milestones) and #33 (warranty claims) — remain `NOT_IMPLEMENTED`, with concrete (not vague) designs and blockers recorded in `docs/FEATURE_MATRIX.md`.** Milestones would need a new `Milestone` storage dataclass and three new methods reusing the existing per-criterion evaluation machinery, bounded by a cap analogous to `MAX_CRITERIA` — a real, implementable, bounded-scope addition, but one that touches the core single-settlement-per-agreement invariant (`settlement_id == ""` guard) in a way that deserves its own dedicated design/test/live-verification cycle rather than being bundled into a pass that already touched seven other capabilities, per the standing instruction to preserve existing guarantees. Warranty claims hit the identical wall-clock-time blocker as #12: there is no trustworthy way to define "the claim window has closed" in this runtime, and the mutual-consent substitute used elsewhere does not fit a warranty's premise (protecting the buyer from a provider who has every incentive to never consent to releasing held funds). Neither was rushed in to inflate the capability count.
    - All of the above (except #30/#33, genuinely not built) are covered by new Direct Mode tests — see `docs/FEATURE_MATRIX.md` for exact test names — with live-network verification following in this same pass once the redeploy completes (see `docs/DEPLOYMENT.md`).

These are recorded here because they are not obvious from the public docs pages and materially changed both the contract's time-handling design and its defensive coding style.

## What this build does NOT claim

This section predates the live Studio Network work recorded above and in `docs/DEPLOYMENT.md`; it is kept for history but superseded on the points below — see `docs/DEPLOYMENT.md`, `docs/FEATURE_MATRIX.md`, and items 10–11 above for the current, accurate status.

- Native-value escrow is now live-verified, not merely unverified-by-default: it was live-tested, found to fail for a specific root-caused reason, fixed in source using the correct GenVM primitive, redeployed, and fully live-verified with real deposits, a real settlement, a real appeal bond, and real GEN withdrawals — see items 10–11 and `docs/DEPLOYMENT.md` "Native-value escrow: live-verified".
- Live network deployment and real multi-validator consensus have since been exercised extensively — five complete real agreement lifecycles, `FINALIZED` under genuine 5-validator consensus, across both evaluation profiles (`docs/DEPLOYMENT.md`).
- Not all 38 numbered capabilities are `IMPLEMENTED_VERIFIED`. See `docs/FEATURE_MATRIX.md` for the current per-capability status; several Tier 2/3 capabilities are `PARTIAL` or `NOT_IMPLEMENTED` and are described honestly rather than padded to a "38/38" claim.
