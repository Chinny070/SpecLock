# SUBMISSION

## What SpecLock is

A single canonical GenLayer Intelligent Contract (`contracts/speclock.py`) for universal digital-delivery agreement and adjudication, with two fully-implemented evaluation profiles (API delivery, AI-agent delivery) sharing one typed lifecycle/evidence/evaluation/appeal/settlement state machine.

## What consensus actually protects here — now proven live, not just by design

For every criterion judgment, the leader's observation is independently re-derived by every validator (`gl.vm.run_nondet_unsafe` with a custom validator function — see `docs/CONSENSUS.md`) and only the decision-critical fields are compared, never the leader's narrative alone. This is no longer only a design claim: **four complete agreement lifecycles were executed and settled on GenLayer Studio Network, across both evaluation profiles**, each `create_agreement → accept_agreement → fund_agreement → freeze_agreement → submit_evidence → request_evaluation → finalize_verdict ×2 → settle`, every step `FINALIZED` under real multi-validator consensus.

API-delivery: real validators independently fetched `https://httpbin.org/status/200` and correctly derived `overall_finding:"FAIL"` (reachable, HTTP 200, non-JSON body); real validators independently fetched `https://httpbin.org/json` and correctly derived `overall_finding:"PASS"`. Both settled exactly matching the deterministic rules (`FAIL` → full refund to buyer; `PASS` → full release to provider).

AI-agent-delivery: real validators independently fetched `https://httpbin.org/robots.txt` and the LLM's rationale genuinely quoted the fetched content, deriving `overall_finding:"PASS"` for a matching criterion. For a second criterion that described an artifact never actually delivered, the model did **not** guess `FAIL` — it correctly returned `UNVERIFIABLE`, unscripted real reasoning, which in turn correctly triggered `settle()`'s fund-recovery branch (`terminal_phase:"RECOVERY_PENDING"`, full amount retained, neither party credited) rather than awarding anyone on an inconclusive verdict.

No outcome across any of the four was assumed in advance — all were read back from the chain after each evaluation actually executed. Full transaction-by-transaction evidence in `docs/DEPLOYMENT.md`.

## What a dedicated security audit of this contract found and fixed

A follow-up review specifically asked whether an untrusted caller could manipulate deadlines, appeal windows, or settlement timing. The original design (a caller-supplied `now` timestamp checked against a monotonic ratchet) **could not be proven safe** — a self-interested party could always choose a value that served them, in either direction. It has been replaced: no part of this contract depends on any party's claim about elapsed time. `finalize_verdict` (from a provisional verdict with no appeal) and the FROZEN branch of `cancel_or_expire` now require both buyer and provider to separately consent before taking effect, which a lone party cannot force. `file_appeal` was never time-boxed to begin with. This mutual-consent mechanism was exercised live on both real settled agreements above (each `finalize_verdict` was called once per party; the first call returned `false`, the second `true`). See `DECISION.md` item 1, `docs/THREAT_MODEL.md` "clock redesign", and `tests/direct/test_speclock_security.py::test_finalize_consent_cannot_be_forced_by_a_single_malicious_party`.

The same review pass also found and fixed a real defect in `resolve_appeal` (an appeal would always resolve `UPHELD` on the first round regardless of outcome — see `docs/CONSENSUS.md` "Appeal resolution precision") and, during live Studionet testing, a real defect in `_as_address` (`TypeError: string argument without an encoding` when an address argument arrived as a plain hex string, the convention used by `genlayer-js`'s standard API — see `DECISION.md` item 7). Both are fixed and covered by regression tests.

## Native-value escrow: failed, root-caused, fixed, redeployed

A first payable-deposit / `emit_transfer`-payout escrow design was implemented and deployed for live testing (`0xaa54c150B128843e5638cF31e2F1B632117ccBE2`). **Deposits genuinely worked**: a disposable test wallet's real balance dropped by exactly the amount sent. **Payouts did not**: the transfer to a plain wallet (EOA) recipient reached `FINALIZED` with `result_name:"NO_MAJORITY"` and a leader-receipt result that decodes to `"Contract ... not found"`.

**This was then root-caused and fixed, not merely documented as a limitation.** `gl.get_contract_at(address)` addresses another GenLayer *intelligent contract* — it is the wrong primitive for paying a plain wallet, and its failure there is correct, expected behavior. The fix, `gl.evm.contract_interface` (an EVM-layer proxy, `_EthAccount` in `contracts/speclock.py`), was found by inspecting a sibling project in this account, AgentCourt, which solved the identical problem on the identical pinned runner and network with real, live proof: a disposable wallet's balance genuinely moved via this exact call. `fund_agreement`/`file_appeal` are payable again; `_settle`/`resolve_appeal` credit a pull-payment `claimable` balance; a new `withdraw()` method pays it out via `_EthAccount`. This is covered by 8 new Direct Mode tests — **52/52 tests pass**, lint clean.

**Two redeploy attempts to verify this for SpecLock itself initially looked blocked, then turned out to be a CLI invocation mistake, not a platform or contract issue.** Both fresh deployments reached `status_name: "FINALIZED"` with real 5-validator consensus — which a first pass mistook for success — but their leader receipts actually carried `execution_result: "ERROR"`, decoding to `TypeError: SpecLock.__init__() takes 1 positional argument but 2 were given`. Comparing raw deploy calldata byte-for-byte against the working deployment found the cause: the deploy command used `--args '[]'`, and the CLI's variadic `--args` flag passed that single-quoted shell token through as one literal string constructor argument, not an empty array. Corrected by omitting `--args` entirely (matching AgentCourt's own documented working invocation), redeployed to `0xbE2a98135e41B4fE722919b87024D867F8De8343` (`FINALIZED`, `execution_result: "SUCCESS"`, confirmed via a working `genlayer schema` readback).

**Then fully live-verified with real GEN moving in both directions.** Two complete agreements were run under an explicit budget (max 0.001 GEN per transaction, max 0.02 GEN cumulative; actual spend 0.00068 GEN): a real `PASS` settlement where the provider called `withdraw()` and received a real payout — independent `getBalance` check showed the provider's wallet increase by exactly the settled amount — and a real `FAIL` settlement that was appealed with a real bond, correctly `REJECTED` on re-evaluation against unchanged evidence, with the bond correctly credited to the non-appellant party and withdrawn for real. A second `withdraw()` by the same provider correctly reverted (double-withdrawal prevented); a `withdraw()` by a party with zero claimable balance correctly reverted (no-balance withdrawal rejected). **No contract defects were found** — every outcome matched Direct Mode's existing predictions exactly. Full transaction-by-transaction record: `docs/DEPLOYMENT.md` "Native-value escrow: live-verified".

## Capability audit: all 38 numbered brief items, a real fund-lock bug found and fixed

A full capability-by-capability audit (`docs/FEATURE_MATRIX.md`) traced every one of the 38 numbered capabilities to its implementing method(s), its Direct Mode test(s), and its live-network verification status. Writing a Direct Mode probe for the **full** `request_resubmission` cycle — something no existing test exercised — found that `submit_evidence` never advanced the agreement's phase out of `RESUBMISSION_REQUESTED`, so a new evaluation could never be requested again: a genuine, previously-untested fund-lock, with no escape since `cancel_or_expire`'s wind-down also only accepted `FROZEN`. A related defect meant that even after fixing the phase transition, a resubmission's corrected evidence was silently ignored on re-evaluation (the API evaluator always re-probed the first, stale evidence for a criterion rather than the latest). Both fixed, covered by two new regression tests, 54/54 tests pass. Redeployed and **live-verified end to end**: a real agreement evaluated `FAIL`, was resubmitted, corrected evidence was submitted, and re-evaluation produced a genuine `PASS` — exactly the fix, proven live.

This audit also credited several capabilities with live evidence already gathered in earlier runs that the matrix had never reflected (appeal, evidence freeze, finding-specific challenges, web-evidence fetching, evidence-quality bands), and ran two more small live transaction batches to close remaining gaps: multi-criterion scoring (a real two-criterion agreement correctly derived overall `FAIL` from mixed `PASS`/`FAIL` findings), ambiguity detection (a real vague-term spec was flagged and the freeze-acknowledgement gate was live-tested both ways), reputation tracking (read back before/after a real finalize), and policy-fingerprint read-back. **30 of 38 capabilities are now `IMPLEMENTED_VERIFIED`** on a live network (up from 15 before this audit) — see `docs/FEATURE_MATRIX.md` for the complete table.

## Unresolved risks (ranked, smallest safe next action first)

1. **Two capabilities genuinely not implemented**: milestones (`docs/FEATURE_MATRIX.md` #30) and optional warranty claims (#33). Both are real, scoped feature additions (a milestone ledger of sub-agreements; a claim-window design on retained funds) — not attempted in this pass rather than rushed or faked. Native-value custody (the prerequisite for both) is now live-verified, so these are purely a scope/time choice, not a blocked dependency. Not required for a Tier 1 release per the brief's own prioritization.
2. **One capability (#13, real `PARTIAL` settlement split) cannot be forced live.** The deterministic API evaluator never emits `FINDING_PARTIAL`; only the agent profile's LLM judge can, nondeterministically. Forcing it live would mean gambling transaction budget on an uncontrollable model output rather than a deterministic result, so it remains Direct-Mode-only, honestly — not a correctness gap.
3. **Re-evaluation on appeal re-runs every criterion, not just the challenged ones** (`docs/FEATURE_MATRIX.md` #26) — a reasonable efficiency/precision follow-up, not a correctness defect (the resolution comparison itself is now precise and live-verified).
4. **One keystore password exposed in git history** (see credential-exposure audit above) — low value (testnet-only account), cannot be scrubbed without rewriting history (not done, per no-force-push policy); the account should simply not be reused.
5. **A `withdraw()` payout that fails after `claimable` is zeroed cannot be reconciled from on-chain state alone** (see `docs/SECURITY.md` "Residual risk"). A liveness/availability risk, not an integrity one — no double-spend, no unauthorized redirection possible. Shared with AgentCourt's identical pattern; not fixable without a GenVM-side transfer-result callback, which does not appear to exist in the installed SDK.
6. **A small amount of real testnet GEN (0.0001 GEN) is stranded** in one agreement on the current deployment, due to the same disposable-key-lifetime limitation documented throughout this project (a transient RPC error during receipt-polling meant a lifecycle couldn't be completed in the same process, and the keys cannot be reused from a new one). Low value, same established pattern, not a new risk class.
