## Deadline / time-source conclusion (re-audited)

The earlier conclusion that the installed test harness could not verify a trustworthy time source was incomplete. The current official transaction-context documentation explicitly guarantees transaction-pinned `datetime.now(timezone.utc)` and identical values for validators; Direct Mode's `warp()` characterization confirms the harness behavior. The current local candidate uses that time for delivery, appeal, resubmission, warranty, and milestone deadlines. It never accepts a caller-supplied timestamp. Tests prove early party-only finalization is rejected, permissionless finalization after the appeal deadline, rejection of late evidence, full refund after an expired delivery window, and release of an unclaimed warranty holdback after its claim window.

These changes are local-only pending a deployment and live transaction verification. The currently documented Studionet release does not contain them. The timestamp remains the transaction's timestamp rather than present wall-clock time; elapsed windows are measured from a finalized on-chain transaction timestamp.
